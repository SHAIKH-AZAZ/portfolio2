Hard problem 1

A drawing is written for people, not programs.

A structural drawing tells you the steel in a beam with a short label such as 2L-T8-150 C/C. An engineer reads it in a second. A program has to be taught every way it can be written.

1The problem

Someone reads each label off the drawing and types the bars into a sheet, beam after beam, floor after floor. It is slow, and one misread digit quietly changes the steel order.

2Why it is hard

There is no fixed format. 2L-T8-150 C/C, T8@150 and 8Φ @ 150 c/c all mean the same bar. Labels also leave things out, and a wrong guess looks exactly like a right answer.

3How I solve it

Treat the label as a small language: reduce every spelling to one form, read it into fields, then check each field against what steel actually exists.

When something is missing, say what was assumed. When it can't be read, flag it, never guess.

Hard problem 2

Steel comes in 12 m bars. Buildings don't.

A schedule asks for hundreds of pieces in a dozen lengths. Every one has to be cut from a standard bar, and whatever is left at the end of a bar is steel that was paid for and thrown away.

1The problem

On site, bars are usually cut in the order the schedule lists them. That is easy to follow, but it leaves a long tail on bar after bar.

2Why it is hard

The number of ways to fill one bar grows very fast with each new length, and the best cut for this bar can ruin the next one. Trying everything is not an option on a real schedule.

3How I solve it

Search the ways to fill one bar, keep the one with the smallest tail, repeat it while the demand lasts, then search again.

A simple plan runs alongside as a floor, so the result is never worse than the easy way. Bad input is rejected before the search starts.

Hard problem 3

Right today is easy. Still right after the next change is the job.

People order steel from these numbers. A formula that is off by one bend is not a bug report, it is a truck of wrong bars. So I write the checks along with the code.

1The problem

The same bar length shows on the screen, in the Excel export and in the cutting report. Change the rule in one place and the three can silently disagree.

2Why it is hard

The failures are quiet. Nothing crashes. A number is simply a little wrong, and the first person to notice is standing next to a bending machine.

3How I solve it

Work each case by hand first, then pin it as a check. Test the edges on purpose: zero, too long, missing, written oddly.

Run every check on every merge, and deploy only when they pass.

How I work through a problem.

Find the person who does it by hand

Watch the real steps and write down the limits that never move: 12 m stock, a cover dimension, a code rule. Everything else obeys those.

Work one case on paper

If I can't get the answer by hand, I can't tell whether the code is right. The hand-worked case becomes the first test.

Ship the smallest version that is real

One element working end to end, from input to export, beats four half-finished ones. Then widen it.

Try to break it

Zero, negative, too long, missing, written oddly. Each failure found here is one a user never sees.
